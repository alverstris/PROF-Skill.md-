## Path confinement and backup before mutation

`checked_path()` checks each existing ancestor and final component using `lstat`, rejects symlinks and Windows reparse attributes, and requires resolved identity to equal the absolute spelling. `child()` confines a descendant to its checked root. Package paths reject traversal, absolute paths, backslashes, ADS/colon syntax, control characters, noncanonical spelling, trailing spaces/dots and reserved Windows device components. Both inventory and Git-tree validation detect case-folded collisions and nonordinary entries. Manifest controls may use the actual legitimate parent references, but resolution must remain inside the package.

The production wrapper supplies only the canonical authorized target, a stage below the fresh preparation run and a new dated backup below the fixed backup root. Prior to any replacement, `install_transaction()` verifies staged bytes and manifests, saves the complete old installed inventory, saves an attempt record with a hold, copies the full installation to a new external backup, and verifies both backup bytes and unchanged original bytes. The backup and failed/displaced installation evidence are retained; there is no recursive deletion or cleanup of those records.

These are point-in-time guards, not filesystem locks against a concurrent external actor. The current helper, preparation path and installed paths were inspected in their actual canonical locations. The task does not require a hostile-agent sandbox or protection against deliberately relocating/rewriting the program outside its instructed workflow.

## Replacement, fallback and rollback

The first replacement method moves the whole old installation to `previous-installation/` and promotes the verified stage. This handles obsolete installed files without leaving them in the destination. If the initial directory move raises an actual `OSError`, the exact type, message, errno and Windows error are retained. A fallback is allowed only if the old installation is still unchanged, no displaced directory exists, the verified backup is intact and old/staged relative file sets are exactly equal. It then replaces every file as raw binary bytes through checked ordinary source/destination paths. An extra obsolete file blocks this fallback.

The success path rechecks the full installed file inventory and raw identities, manifests against the staged result, intact backup and live main pin. It saves complete verification and a current false generation hold. Failure after mutation attempts restoration before trying to persist failure records, so a status-record error cannot skip restoration. Restoration uses the preserved verified backup, first trying whole-directory retention of the failed installation and a full backup copy; a blocked move permits byte restoration only for the exact original file set. The original complete backup is kept. Failed restoration is explicitly marked for manual recovery and generation remains held. A success record already written before a later transaction failure is preserved separately and invalidated when records can be saved.

The final draft includes the critical ordering above. A preceding in-progress draft placed a hold-record write before restoration; it was already corrected by the owner before the final review. The final success of a separate `verify-installed` also writes a fresh false current hold. No issue from those earlier draft states is being attributed to the final helper.

`verify-installed` is deliberately read-only with respect to the installation. It rechecks the original stage binding, successful installation pin, live main, full installed bytes, actual manifests and complete backup. A failed readback writes a hold and failure record; it does not claim automatic restoration from this separate read-only command. Root must preserve the backup and resolve the cause. A later complete successful readback may clear the hold while the older failure record remains as history. The README's detailed final-readback instructions and required successful exits govern readiness; an older pass file alone is insufficient.
