Synthetic fixed-route retrieval launcher probe — 2026-10-12

Scope and outcome
The probe uses only locally generated non-subject text and a 160 by 100 pixel geometric PNG. No lecture source, teaching source, report source, GitHub, browser, package mutation, or new subject input to a SASIS was used. The operative demonstration is verified-live/. The 138 automated checks in test_results.json passed. The live route then completed with a separate actual view_image call and locally persisted return evidence.

Interface and order
Each retrieval invocation is the absolute fixed executable path followed by exactly one predeclared step ID. No input pathname, byte range, hash, interpreter choice, or command is accepted from the reader. The initial route is text-01 (synthetic baseline), figure-01 (synthetic baseline), inspect-01 (receipt), text-02 (synthetic teaching-stage placeholder). The predeclared revisit-text-01 ID can re-fetch only the already-read baseline text slice and does not advance the cursor. It rejects before the initial read and while a figure receipt is pending. Ordinary repeated or skipped route steps reject.

The executable embeds its route and pinned SHA-256. route.json is a review copy, not a runtime input. The generated executable is mode 0555; route.json and provision_manifest.json are mode 0444. Configuration is immutable by the operating procedure and checked against its embedded pin; these ordinary permissions and pins are not an adversarial immutability boundary. A fresh actual-source run must prepare and preflight its own launcher under its applicable protocol. This prototype is archival evidence, not a launcher for real teaching inputs.

Evidence
launcher_template.py and provision.py preserve the source and exact fixture construction. tests-v2/ preserves each separately provisioned malformed or normal route, its executable, fixture bytes, call arguments, stdout, stderr, state, and audit log. test_results.json contains every check. The earlier version is retained in version-1-source/, tests/, and live/. The first real view returned a data URL labeled application/octet-stream, which the first receipt schema rejected; no subsequent route content was released there. The corrected fresh launcher accepts the tool's observed return MIME while retaining all receipt binding checks.

verified-live/audit.jsonl records attempted fixture opens, successful opens, exact requested and actual byte ranges, actual byte counts and SHA-256 values, verification, and emission authorization. Its raw tool transcripts preserve actual exec invocations/results. verified-live/actual_view_tool_record.json preserves the actual view invocation, full raw returned data URL, and observed result metadata. verified-live/receipts/figure-01.json is a separate externally recorded receipt bound to that run and full image. The live view result displayed the entire synthetic PNG. The launcher required the receipt before allowing text-02. The local orchestrator wrote the receipt after the actual tool result; no inter-agent receipt communication was required.

The Python audit hook records fixture open attempts within the launcher process. Tests demonstrate zero fixture opens for unknown, skipped, extra/missing, malformed, repeated, premature-revisit, and receipt-blocked calls. Runtime truncation, content corruption, and oversized image tests open only the pinned fixture, record actual bytes/hash, and reject without content output. The full exact image is delivered before its separate view stage. live_verification.json checks the current invocation's audit ordering and complete live sequence. sealed_inventory.json contains hashes of preserved files.

Concrete limitations
This is a workflow guard for its own executable, not technical confinement of exec, view, the filesystem, or the agent. An operator with filesystem access can replace the launcher, fixtures, state, receipts, or logs, or invoke other readers. The embedded expected digest has no independent trust anchor; mode bits are reversible. Logs are unsigned local records, not tamper-evident external evidence. The audit hook is Python-process evidence, not a whole-machine audit. O_NOFOLLOW protects the final fixture path component, not replacement of ancestor directories. The prototype caps its route at 20 steps, text slices at 4096 bytes, and sources/images at 1 MiB. These synthetic probe limits do not constitute admission of a next actual reader or a production route.

The seal verifier initially grouped events by PID, but independent exec namespaces reused PID 2. That false-negative check and its script are retained. The corrected verifier groups this sequential live trace by the process_sequence restart at 1. This is suitable for this recorded sequential trace, not a claim that PID or sequence alone is a universal concurrent audit identifier.

The receipt validator checks fields, run/image binding, and route order. It does not authenticate that the view tool ran or prove semantic visual inspection. Automated test receipts are conspicuously marked synthetic_test_acknowledgement; the verified-live receipt is based on an actual tool return. The current generic template permits synthetic test acknowledgements for exercising the gate. An arbitrary operator can forge either form. A task-specific production protocol must require preservation of actual invocation/result evidence, not treat the driver's receipt acceptance alone as proof.

The image receipt path in this task-specific template is fixed to synthetic_figure.png. Broader image naming is not implemented even though the validation pattern would admit other synthetic PNG filenames. Delivered files and receipts can change externally. The driver cannot guarantee what a later view tool sees without checking that external result. The live verifier separately compares the actual returned image bytes with the delivered image.

Text state advances immediately before stdout emission, after verified reading and durable emission authorization. A crash or broken pipe can therefore consume a step without a completed stdout write. The cursor tracks authorization to emit, not acknowledged delivery. Recovery requires an explicit authorized procedure; this demonstration provides only its bounded baseline revisit, not a general replay or recovery mechanism. No successful output event is claimed where absent.

Suggested short protocol wording
Before reading, provision and preflight one fixed launcher with the complete ordered route and pinned hashes. During reading, invoke only that launcher plus the next predeclared step ID. The launcher must reject invalid, skipped, repeated, or extra arguments before opening any source, read only the next fixed bounded binary slice, and record the actual bytes and hash before release. Predeclared baseline revisit IDs may re-read only previously verified baseline slices without advancing the cursor. For figures, deliver the complete pinned image and hold advancement until a separate receipt stage records the local view tool's actual invocation and result, bound to the run and image. These checks govern the procedure; they do not confine independent tools or prove semantic inspection.
